# JPA 6주차 학습 정리 

## 1. 엔티티 설계에서 고려할 사항

엔티티는 데이터의 상태와 연관관계를 표현하므로, 변경 가능성과 조회 방식까지 고려해 설계해야 한다.

| 설계 항목 | 적용 원칙 | 이유 및 참고 사항 |
| --- | --- | --- |
| 상태 변경 | Setter 사용을 가능한 한 제한 | 값이 어디에서 변경되는지 추적하기 쉽도록 변경 의도를 드러내는 메서드를 사용한다. |
| 연관관계 조회 | 기본적으로 지연 로딩(LAZY) 적용 | 즉시 로딩은 예상하지 못한 시점에 관련 엔티티를 조회할 수 있어 동작을 예측하기 어렵다. |
| 컬렉션 관리 | 컬렉션 필드 선언 시 초기화 | 컬렉션을 일관된 상태로 관리하고 null 관련 문제를 줄인다. |
| DB 이름 매핑 | 테이블·컬럼명 생성 규칙 확인 | JPA와 Hibernate의 네이밍 전략에 따라 실제 생성되는 이름이 달라질 수 있다. |

### 테이블 및 컬럼 네이밍 전략

엔티티 클래스명과 필드명이 데이터베이스의 테이블명·컬럼명으로 변환되는 규칙을 확인해야 한다. Hibernate의 기존 구현에서는 엔티티 필드명을 컬럼명으로 그대로 사용하는 방식이 있으며, Spring Boot의 설정에 따라 다른 명명 규칙이 적용될 수 있다.

## 2. 구현할 핵심 기능

이번 애플리케이션은 회원, 상품, 주문을 중심으로 구성한다.

| 기능 영역 | 세부 기능 |
| --- | --- |
| 회원 관리 | 신규 회원 등록, 회원 정보 조회 |
| 상품 관리 | 상품 등록, 기존 상품 정보 수정, 상품 조회 |
| 주문 관리 | 상품 주문, 주문 이력 조회, 주문 취소 |

## 3. 애플리케이션 구조

역할에 따라 코드를 구분하는 **계층형 아키텍처**를 사용한다. 웹 요청 처리부터 데이터 접근까지 책임을 나누어 구성한다.

```text
Controller / Web  →  Service  →  Repository  →  DB
                         ↓             ↓
                      Domain(엔티티)
```

| 계층 | 주요 책임 |
| --- | --- |
| Controller / Web | 사용자 요청을 받아 처리하고 웹 응답을 구성 |
| Service | 비즈니스 로직 실행 및 트랜잭션 관리 |
| Repository | EntityManager를 활용한 JPA 데이터 접근 |
| Domain | 엔티티 정의 및 여러 계층에서 사용하는 도메인 모델 관리 |

### 패키지 구성 예시

기본 패키지는 `jpabook.jpashop`이며, 하위 패키지를 기능과 역할에 맞게 분리한다.

```text
jpabook.jpashop
├── domain       # 엔티티 및 도메인 모델
├── exception    # 예외 관련 코드
├── repository   # 데이터 접근 로직
├── service      # 비즈니스 로직 및 트랜잭션
└── web          # 웹 요청 및 응답 처리
```

## 4. 권장 구현 흐름

**리포지토리·서비스 구현 → 테스트 케이스 작성 및 검증 → 웹 계층 연결** 순서로 진행한다.

먼저 데이터 접근과 핵심 비즈니스 로직을 완성한 다음, 테스트로 기능이 올바르게 작동하는지 확인한다. 이후 웹 계층을 추가하면 화면이나 요청 처리 코드와 분리된 상태에서 주요 로직을 검증할 수 있다.

## 핵심 정리

엔티티의 무분별한 상태 변경을 피하고 연관관계는 지연 로딩을 기본으로 설계한다. 컬렉션 초기화와 DB 명명 규칙도 함께 점검한다. 애플리케이션은 웹·서비스·리포지토리·도메인으로 역할을 나누고, 핵심 로직을 테스트한 후 웹 기능을 연결한다.
