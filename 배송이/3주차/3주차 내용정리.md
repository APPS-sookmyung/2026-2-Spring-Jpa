# 3주차 - JPA 기초 Section 2

## 08. 값 컬렉션 Set 매핑

하나의 엔티티가 여러 개의 값을 가질 때 `Set` 형태로 매핑할 수 있다.

``` java
@ElementCollection
@CollectionTable(
    name = "role_perm",
    joinColumns = @JoinColumn(name = "role_id")
)
@Column(name = "perm")
private Set<String> permissions = new HashSet<>();
```

-   `@ElementCollection` : 엔티티가 아닌 값 컬렉션 매핑
-   `@CollectionTable` : 컬렉션 값을 저장할 테이블 지정
-   `@JoinColumn` : 원본 엔티티의 ID와 연결
-   `@Column` : 실제 값이 저장되는 컬럼

기본 Fetch 전략은 `LAZY`이다. 엔티티를 먼저 조회하고 실제 컬렉션에
접근할 때 컬렉션 테이블을 조회한다.

`@Embeddable` 타입도 Set에 넣을 수 있으며, 이 경우 `equals()`와
`hashCode()` 구현이 중요하다.

## 09. 값 컬렉션 List 매핑

List는 Set과 비슷하지만 **순서가 존재한다.**

``` java
@ElementCollection
@CollectionTable(
    name = "question_choice",
    joinColumns = @JoinColumn(name = "question_id")
)
@OrderColumn(name = "idx")
@Column(name = "text")
private List<String> choices = new ArrayList<>();
```

-   `@OrderColumn` : List의 순서를 DB 컬럼에 저장
-   인덱스는 `0, 1, 2 ...` 형태로 저장
-   부모 엔티티가 삭제되면 해당 값 컬렉션도 함께 삭제된다.

## 10. 값 컬렉션 Map 매핑

Map은 Key와 Value를 함께 저장한다.

``` java
@ElementCollection
@CollectionTable(
    name = "prop",
    joinColumns = @JoinColumn(name = "entity_id")
)
@MapKeyColumn(name = "prop_key")
@Column(name = "prop_value")
private Map<String, String> props = new HashMap<>();
```

`@MapKeyColumn`을 이용해 Map의 Key가 저장될 컬럼을 지정한다.

### 값 컬렉션 정리

-   Set → `@ElementCollection` + `@CollectionTable`
-   List → `@ElementCollection` + `@CollectionTable` + `@OrderColumn`
-   Map → `@ElementCollection` + `@CollectionTable` + `@MapKeyColumn`

## 11. 값 컬렉션 사용 시 주의사항

값 컬렉션은 편리하지만 목록 조회에서 성능 문제가 생길 수 있다.

예를 들어 역할 목록을 조회한 뒤 각 역할의 권한까지 조회하면 엔티티마다
추가 쿼리가 반복될 수 있다. 특히 페이징이 필요하거나 컬렉션 전체가
필요하지 않은 화면이라면 별도의 조회 방식을 고려하는 것이 좋다.

### CQRS

변경 기능과 조회 기능을 분리하는 방식이다.

-   변경 기능 → JPA
-   조회 기능 → JPA, JPQL, JdbcTemplate, MyBatis 등 상황에 맞게 선택

모든 조회 기능을 반드시 JPA 엔티티 모델만으로 구현할 필요는 없다.

## 12. 영속성 컨텍스트 & 라이프사이클

영속성 컨텍스트는 `EntityManager`가 엔티티를 관리하는 메모리 공간이다.
JPA는 이곳에서 엔티티를 보관하고 변경 사항을 추적한다.

``` java
User first = em.find(User.class, id);
User second = em.find(User.class, id);
```

같은 영속성 컨텍스트에서 동일한 ID를 조회하면 같은 객체를 반환할 수
있다.

``` java
first == second
```

이를 **1차 캐시와 동일성 보장**이라고 볼 수 있다.

### 엔티티 상태

``` text
비영속
  ↓ persist()
영속(Managed)
  ↓ detach(), close()
분리(Detached)
  ↓ merge()
다시 영속
```

-   영속 상태 → 변경 추적 O
-   분리 상태 → 변경 추적 X

대량 데이터를 한꺼번에 수정하는 경우에는 변경 감지보다 직접 쿼리를
사용하는 것이 적절할 수 있다.

## 13. 엔티티 연관 매핑

연관관계는 하나의 엔티티가 다른 엔티티 객체를 참조하는 것이다.

``` java
class Review {
    private Hotel hotel;
}
```

대표적인 관계는 `1:1`, `N:1`, `1:N`, `M:N`이며 단방향과 양방향 관계가
존재한다.

연관관계를 사용하기 전에는 다음을 먼저 고려한다.

1.  `@Embeddable`로 표현할 수 있는가?
2.  객체 대신 ID만 참조해도 되는가?
3.  조회 전용 쿼리가 더 적절한가?

## 14. 1:1 단방향 연관 매핑

### 참조키 방식

``` java
@OneToOne
@JoinColumn(name = "hotel_id")
private Hotel hotel;
```

-   `@OneToOne` : 1:1 관계 지정
-   `@JoinColumn` : 외래키 컬럼 지정

`@OneToOne`의 기본 Fetch 전략은 `EAGER`이다.

### 식별자 공유 방식

두 테이블이 같은 PK를 사용하는 경우 `@PrimaryKeyJoinColumn`을 사용할 수
있다.

``` java
@OneToOne
@PrimaryKeyJoinColumn
private Hotel hotel;
```

## 15. N:1 단방향 연관 매핑

여러 Review가 하나의 Hotel을 참조하면 N:1 관계이다.

``` java
@ManyToOne
@JoinColumn(name = "hotel_id")
private Hotel hotel;
```

``` java
review.setHotel(hotel);
em.persist(review);
```

조회 후에는 `review.getHotel()`처럼 연관된 객체에 접근할 수 있다.

`@ManyToOne`의 기본 Fetch 전략 역시 `EAGER`이다.

## 16. 1:N 단방향 연관 매핑

하나의 엔티티가 여러 엔티티를 컬렉션으로 가지는 구조이다.

### Set

``` java
@OneToMany
@JoinColumn(name = "question_id")
private Set<Choice> choices = new HashSet<>();
```

### List

``` java
@OneToMany
@JoinColumn(name = "question_id")
@OrderColumn(name = "list_idx")
private List<Choice> choices = new ArrayList<>();
```

### Map

``` java
@OneToMany
@JoinColumn(name = "question_id")
@MapKeyColumn(name = "map_key")
private Map<String, Choice> choices = new HashMap<>();
```

List는 `@OrderColumn`으로 순서를 저장하고 Map은 `@MapKeyColumn`으로
Key를 저장한다.

## 17. 영속성 전파 & 연관 고려사항

연관관계가 있다고 해서 연관된 새 엔티티가 자동으로 저장되는 것은 아니다.

부모 엔티티의 영속성 작업을 연관 엔티티에도 전달하려면 Cascade를 사용할
수 있다.

``` java
@OneToMany(cascade = CascadeType.PERSIST)
private Set<Choice> choices;
```

대표적인 타입은 다음과 같다.

-   `CascadeType.PERSIST`
-   `CascadeType.REMOVE`
-   `CascadeType.MERGE`
-   `CascadeType.ALL`

Cascade는 엔티티의 생명주기를 연결하므로 특별한 이유가 없다면 신중하게
사용한다.

### 연관관계 설계 시 고려할 점

1.  연관 객체 대신 ID 값 참조 고려
2.  복잡한 조회는 전용 쿼리나 조회 모델 고려
3.  엔티티가 아닌 값 타입인지 확인
4.  1:N보다 N:1 구조 우선 고려
5.  불필요한 양방향 관계 지양

## 전체 정리

-   **값 컬렉션** : `@ElementCollection`을 이용해 Set, List, Map을 별도
    테이블에 저장
-   **영속성 컨텍스트** : 엔티티를 관리하고 변경 내용을 추적
-   **연관관계** : `@OneToOne`, `@ManyToOne`, `@OneToMany` 등으로 엔티티
    연결
-   **Cascade** : 부모의 영속성 작업을 연관 엔티티에 전파

JPA의 기능을 무조건 많이 사용하는 것보다 데이터의 성격과 조회 방식에
맞게 필요한 기능만 선택하는 것이 중요하다.
