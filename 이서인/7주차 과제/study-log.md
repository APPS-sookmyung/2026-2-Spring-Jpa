# 앱스 JPA 스터디 강의 내용 요약

## Spring JPA – 회원과 상품 도메인 개발

이번 강의에서는 앞서 설계한 도메인 모델을 바탕으로 회원과 상품 관리 기능을 실제로 구현하는 방법을 학습하였다. 회원 기능은 Repository, Service, Test 순서로 개발하며, 상품 기능에서는 재고 관리 로직과 예외 처리, 데이터 저장 및 조회 과정을 다루었다.

### 4. 회원 도메인 개발

#### 4-1. 회원 Repository 구현

회원 Repository는 JPA의 `EntityManager`를 활용하여 데이터베이스에 접근하는 역할을 담당한다.

- save(): `persist()`를 이용해 새로운 회원 정보를 저장한다.
- findOne(): 회원 ID를 기준으로 특정 회원을 조회한다.
- findAll(): JPQL을 사용하여 전체 회원 목록을 조회한다.
- findByName(): 이름을 조건으로 특정 회원을 검색한다.
- @Repository: 클래스를 스프링 빈으로 등록하고 JPA 관련 예외를 스프링 예외로 변환한다.
- @PersistenceContext: JPA의 `EntityManager`를 주입받는다.

JPQL은 SQL과 유사하지만 데이터베이스 테이블이 아닌 엔티티를 대상으로 조회한다는 특징이 있다.

#### 4-2. 회원 Service 구현

회원 Service에서는 회원가입과 조회 등의 비즈니스 로직을 처리하고 트랜잭션을 관리한다.

- 회원가입: 신규 회원의 중복 여부를 확인한 후 Repository를 통해 저장한다.
- 중복 회원 검증: 같은 이름의 회원이 존재하면 `IllegalStateException`을 발생시켜 가입을 제한한다.
- 회원 조회: 전체 회원 목록 또는 특정 회원 정보를 조회한다.
- @Service: 해당 클래스를 서비스 계층의 스프링 빈으로 등록한다.
- @Transactional: 데이터 변경 작업이 하나의 트랜잭션 안에서 이루어지도록 관리한다.

조회 중심의 메서드는 `@Transactional(readOnly = true)`를 적용하고, 회원가입과 같이 데이터를 변경하는 메서드에는 별도로 `@Transactional`을 설정한다.

다만 애플리케이션에서 중복 여부를 검사하더라도 동시 요청에 의한 중복 가입 가능성이 있으므로 실제 서비스에서는 DB의 UNIQUE 제약조건을 함께 사용하는 것이 안전하다.

#### 4-3. 의존성 주입 방식

Service가 Repository를 사용하기 위해서는 의존관계를 설정해야 한다. 강의에서는 필드 주입보다 생성자 주입 방식을 권장하였다.

- 생성 시점에 필요한 의존성을 전달받아 안정적으로 객체를 구성할 수 있다.
- `final` 키워드를 사용하여 의존관계가 변경되지 않도록 설정할 수 있다.
- 테스트 코드 작성과 유지보수가 편리하다.
- Lombok의 `@RequiredArgsConstructor`를 활용하면 생성자 코드를 직접 작성하지 않아도 된다.

#### 4-4. 회원 기능 테스트

구현한 기능이 정상적으로 동작하는지 확인하기 위해 회원가입 및 중복 회원 검증 테스트를 작성한다.

- 회원가입 테스트: 회원을 등록한 후 저장된 ID를 통해 동일한 회원이 조회되는지 확인한다.
- 중복 회원 테스트: 동일한 이름의 회원을 두 번 등록했을 때 예외가 발생하는지 검증한다.
- assertEquals(): 예상한 값과 실제 조회 결과가 일치하는지 확인한다.
- assertThrows(): 특정 코드 실행 시 지정한 예외가 발생하는지 확인한다.

또한 `@SpringBootTest`를 사용해 스프링 환경에서 통합 테스트를 진행하고, 테스트에 `@Transactional`을 적용하여 실행 후 데이터가 롤백되도록 설정한다.

테스트 환경은 실제 개발 DB와 분리하는 것이 좋으며, 별도의 테스트 설정 파일이나 H2 메모리 데이터베이스를 활용할 수 있다.

### 5. 상품 도메인 개발

#### 5-1. 상품 엔티티 및 재고 관리

상품 엔티티는 상품명, 가격, 재고 수량 등의 기본 정보를 관리하며, 재고 수량을 직접 변경하는 비즈니스 메서드를 포함한다.

- addStock(): 전달받은 수량만큼 재고를 증가시킨다. 주문 취소 후 재고를 복구하는 경우 등에 활용한다.
- removeStock(): 상품 주문 시 재고를 감소시킨다.
- 재고 감소 후 수량이 0보다 작아지면 `NotEnoughStockException`을 발생시킨다.
- `@Inheritance(strategy = InheritanceType.SINGLE_TABLE)`을 사용하여 상속된 상품 엔티티를 하나의 테이블로 관리한다.

재고 관리 로직을 엔티티 내부에 구현하면 상품의 상태 변경과 관련된 기능을 한곳에서 관리할 수 있다.

#### 5-2. 재고 부족 예외 처리

재고가 부족한 상황을 구분하기 위해 사용자 정의 예외인 `NotEnoughStockException`을 구현한다.

- `RuntimeException`을 상속하여 예외 클래스를 정의한다.
- 재고보다 많은 수량을 주문하는 경우 해당 예외를 발생시킨다.
- 다양한 생성자를 제공하여 예외 메시지나 원인 정보를 전달할 수 있다.

이를 통해 재고 부족 상황을 명확하게 표현하고 일반적인 오류와 구분할 수 있다.

#### 5-3. 상품 Repository 구현

상품 Repository는 상품 데이터를 저장하거나 조회하는 데이터 접근 계층이다.

- save(): 상품 ID를 기준으로 신규 상품과 기존 상품을 구분하여 저장한다.
- persist(): ID가 없는 신규 상품을 영속성 컨텍스트에 저장한다.
- merge(): ID가 있는 기존 상품의 상태를 병합한다.
- findOne(): 상품 ID를 이용하여 특정 상품을 조회한다.
- findAll(): JPQL을 사용하여 전체 상품 목록을 조회한다.

하나의 `save()` 메서드에서 상품의 신규 등록과 기존 상품의 수정 처리를 구분하도록 구현하였다.

#### 5-4. 상품 Service 구현

상품 Service는 Repository를 호출하여 상품 등록과 조회 기능을 제공한다.

- saveItem(): 상품 데이터를 저장하거나 수정하며, 데이터 변경을 위해 `@Transactional`을 적용한다.
- findItems(): 전체 상품 목록을 조회한다.
- findOne(): 상품 ID를 기준으로 특정 상품을 조회한다.
- @Transactional(readOnly = true): 조회 메서드의 읽기 전용 트랜잭션을 설정한다.

상품 Service는 별도의 복잡한 로직을 처리하기보다 Repository에 데이터 접근 작업을 위임하는 비교적 단순한 구조로 구성된다.

### 6. 정리

이번 강의에서는 회원과 상품 도메인을 실제 코드로 구현하면서 Repository와 Service의 역할, 트랜잭션 관리, 생성자 주입, 기능 테스트의 중요성을 학습하였다.

회원 도메인에서는 중복 회원 검증과 테스트를 통해 데이터의 일관성을 확인하는 과정을 다루었으며, 상품 도메인에서는 엔티티 내부에 재고 관리 로직을 구현하고 사용자 정의 예외로 재고 부족 상황을 처리하는 방법을 익혔다.

특히 비즈니스 로직은 Service 또는 Domain에서 처리하고, Repository는 데이터 접근에 집중하도록 역할을 구분하는 것이 이번 강의의 핵심이다. 이를 통해 기능별 책임이 명확하고 유지보수가 편리한 애플리케이션을 구성할 수 있다.
