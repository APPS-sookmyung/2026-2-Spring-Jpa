

### JPA 기초 08. 값 컬렉션 Set 매핑

엔티티가 아닌 단순 값(Basic 타입이나 `@Embeddable`)을 여러 개 저장해야 할 때 사용한다. 예를 들어 Role 엔티티 하나가 여러 개의 권한(String)을 가질 때, 엔티티를 따로 안 만들고 값 컬렉션을 쓴다.

* `@ElementCollection`과 `@CollectionTable`을 써서 별도 테이블(`role_perm`)로 매핑한다.
* 기본 조회 전략은 LAZY(지연 로딩)이다.
* 부모 엔티티 생명주기에 종속적이라 부모가 삭제되면 컬렉션 데이터도 같이 날아간다.
* `@Embeddable` 클래스를 Set에 담을 때는 동등성 비교를 위해 **`equals()`와 `hashCode()` 구현이 필수**다.

### JPA 기초 09. 값 컬렉션 List 매핑

순서가 의미 있는 값들을 컬렉션으로 저장할 때 쓴다.

* Set 매핑과 거의 같은데, 순서 보장을 위해 `@OrderColumn`을 추가해 DB에 인덱스 값(0, 1, 2...)을 같이 저장한다.
* 마찬가지로 지연 로딩이 기본이고, 부모 엔티티 삭제 시 연관 데이터도 함께 삭제된다.

### JPA 기초 10. 값 컬렉션 Map 매핑

Key-Value 형태로 단순 값 모음을 관리할 때 사용한다.

* Key로 사용할 DB 컬럼을 지정하기 위해 `@MapKeyColumn`을 쓴다.
* `map.put()`이나 `map.remove()`로 조작하며, Value 자리에는 Embeddable 객체도 들어갈 수 있다.

### JPA 기초 11. 값 컬렉션 주의사항 & CQRS

값 컬렉션은 편해 보이지만 목록 조회 시 N+1 문제처럼 추가 쿼리가 무더기로 나갈 수 있어서 성능상 위험하다.

* 화면에 단순히 목록을 뿌려주거나 페이징 처리를 할 때는 컬렉션 전체를 객체로 조회하는 게 오히려 손해다.
* 그래서 **CQRS(Command Query Responsibility Segregation)** 개념이 필요하다.
* **상태 변경(CUD):** JPA 도메인 모델 활용
* **복잡한 조회(Read):** DTO로 바로 뽑는 JPQL, MyBatis, JdbcTemplate 활용


* **핵심:** 모든 조회 로직을 굳이 JPA 엔티티로만 구현하려 고집할 필요 없다.

### JPA 기초 12. 영속성 컨텍스트 & 라이프사이클

JPA의 핵심인 `EntityManager`가 엔티티를 관리하는 내부 메모리 공간이다.

* **1차 캐시:** 같은 ID로 조회하면 DB를 안 거치고 메모리에서 꺼내와서 동일성(`==`)을 보장한다.
* **Dirty Checking (변경 감지):** 영속 상태(Managed) 엔티티는 값만 수정해 두면 커밋 시점에 알아서 UPDATE 쿼리가 나간다.
* **라이프사이클:** 비영속 $\rightarrow$ 영속(Managed) $\rightarrow$ 준영속/분리(Detached). 준영속 상태가 되면 값을 바꿔도 DB에 반영되지 않는다.

### JPA 기초 13. 엔티티 연관 매핑 개요

객체 간에 참조 필드를 두어 연결하는 것이다.

* 단순히 "객체 그래프 탐색(`review.getHotel()`)이 편하다"는 이유로 연관관계를 무작정 맺으면 안 된다.
* 설계 시 ① Embeddable로 처리가 안 되나? ② ID 값만 참조하면 안 되나? ③ 별도 조회 전용 쿼리를 쓰는 게 낫지 않나?를 먼저 고려해 봐야 한다.

### JPA 기초 14. 1:1 단방향 연관 매핑

두 엔티티가 1대 1로 매핑되는 구조다.

* **참조키 방식:** `@OneToOne` + `@JoinColumn` 사용
* **식별자 공유 방식:** PK를 공유하는 구조로, `@PrimaryKeyJoinColumn` 사용
* `@OneToOne`은 기본 로딩 전략이 EAGER(즉시 로딩)이라 의도치 않은 조인 쿼리가 나갈 수 있으니 주의해야 한다.

### JPA 기초 15. N:1 단방향 연관 매핑

실무에서 가장 흔하게 쓰이는 기본 연관관계 구조다. (예: 여러 개의 Review가 하나의 Hotel을 참조)

* `@ManyToOne` + `@JoinColumn`으로 매핑한다.
* 기본 로딩 전략이 **EAGER**이다.
* 자식 엔티티에 부모 객체를 세팅(`review.setHotel(hotel)`)한 뒤 저장한다.

### JPA 기초 16. 1:N 단방향 연관 매핑

부모 엔티티 하나가 자식 엔티티 여러 개를 컬렉션으로 갖는 구조다.

* `@OneToMany` + `@JoinColumn`을 기본으로 쓴다.
* List면 `@OrderColumn`, Map이면 `@MapKeyColumn`을 조합한다.
* 다만 1:N 단방향은 자식 테이블에 FK가 있다 보니, 저장/수정 시 어색한 UPDATE 쿼리가 추가로 나가는 단점이 있다.

### JPA 기초 17. 영속성 전파 (Cascade) & 설계 주의사항

부모 엔티티의 상태 변화(저장, 삭제 등)를 연관된 자식 엔티티에도 자동으로 넘겨주는 기능이다.

* `@OneToMany(cascade = CascadeType.PERSIST)` 처럼 설정하면 부모만 `persist()` 해도 자식까지 알아서 같이 저장된다.
* **주의:** 두 엔티티의 라이프사이클이 거의 일치하고 단일 소유자일 때만 제한적으로 써야 한다.
* **최종 설계 팁:** 양방향 매핑은 복잡도만 높이므로 지양하고, **N:1 단방향 위주**로 설계하거나 필요 시 ID만 들고 있는 게 깔끔하다.
